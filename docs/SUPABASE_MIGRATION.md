# Supabase migration — Phase 1: PostgreSQL foundation and QR verification

Target architecture: React/Vite on Vercel + Supabase (Auth, PostgreSQL, Row Level
Security, RPC functions, Edge Functions). The move happens in phases. **Phase 1**
covers only the database foundation, a one-time data copy and the QR verifier.

The PHP/MySQL system is **not changed** by Phase 1. It stays the live system and
the fallback until the new stack passes all tests. Phase 1 adds no registration,
randomizer, auth, business RLS policies, resets, Add Attendee, imports, reports or
exports.

| Path | Purpose |
|---|---|
| `supabase/migrations/20261005090000_holcim_foundation_helpers.sql` | `extensions` schema + pgcrypto, `app_time_zone()`, `set_updated_at()` trigger, `generate_qr_token()` |
| `supabase/migrations/20261005090100_holcim_schema.sql` | the 14 application tables + `migration_import_runs` |
| `supabase/migrations/20261005090200_holcim_security_baseline.sql` | RLS on every table, no policies, all privileges revoked from `anon`/`authenticated` |
| `supabase/migrations/20261008090000_holcim_auth_roles_rls.sql` | Phase 2: Supabase Auth profiles, roles, RLS SELECT policies, auth RPCs (docs/SUPABASE_AUTH.md). Requires Supabase's `auth` schema. |
| `supabase/migrations/20261007090000_holcim_registration_sessions.sql` | Phase 10 registration sessions (twin of MySQL 033), with the same RLS/revoke baseline. The import requires source migration 033. |
| `tools/import-mysql-to-postgres.ts` | one-time MySQL → PostgreSQL copy with built-in verification |
| `tools/verify-qr-migration.ts` | READ-ONLY QR verifier (MySQL or PostgreSQL); manifests compatible with `backend/cli/verify-qr-migration.php` |
| `tools/lib/*.ts`, `tools/tests/*.test.ts` | shared code and tests |
| `frontend/src/services/supabaseClient.ts` | browser client config (not used by the app yet) |

The tools need **Node 22.18 or later**. Node runs the TypeScript files directly,
so there is no build step. Run `cd tools && npm ci` once.

## 1. How the MySQL schema was translated

This is the schema after MySQL migrations 001–032, reviewed table by table. Table
names, column names, ids and relationships stay the same, so rows copy 1:1.

| MySQL | PostgreSQL | Notes |
|---|---|---|
| `INT/BIGINT UNSIGNED AUTO_INCREMENT` PK | `integer/bigint generated by default as identity` | `by default` lets the import keep the old ids. Sequences are moved past them afterwards. |
| other `UNSIGNED` columns | `integer/smallint` + `CHECK (>= 0)` where a negative value is meaningless | The largest ids fit easily in `integer`. |
| `ENUM(...)` | `text` + `CHECK (col in (...))` | Same values. A test compares each enum with its CHECK. Easier to extend than PG enum types. |
| JSON stored as `LONGTEXT` | `jsonb` | The import refuses invalid JSON. jsonb does not keep key order or whitespace; the content is compared as canonical JSON. |
| `DATETIME` | `timestamptz` | See §2. |
| `DATE` | `date` | |
| `ON UPDATE CURRENT_TIMESTAMP` | `BEFORE UPDATE` trigger `set_updated_at()` | Same rules: refreshed on a real change, kept when the statement sets `updated_at` itself. |
| generated `active_lock` + `UNIQUE` (events, event_days) | partial unique index `… WHERE status = 'active'` | Same guarantee: one active event, and one active day per event. |
| unique keys under `utf8mb4_unicode_ci` (email, username, attendee_code, external_identifier) | unique index on `lower(col)` | Case-insensitive like MySQL. See §6 for the differences. |
| `token VARCHAR(64)` (binary comparison) | `text COLLATE "C"` + `CHECK (token ~ '^[A-Za-z0-9_-]{16,64}$')` + `UNIQUE` | Exact, case-sensitive and byte-ordered. See §3. |
| composite FKs `(attendee_id, event_id)`, `(event_day_id, event_id)` | the same composite FKs, with `UNIQUE (id, event_id)` on the parent tables | A scan, draw or eligibility row cannot point at another event's day or attendee. |
| FK without `ON DELETE` (MySQL defaults to RESTRICT) | `ON DELETE RESTRICT` | `schema.test.ts` checks every FK's columns, target and rules against MySQL. |
| `schema_migrations` | not copied | Supabase tracks its own migrations. The import stores the MySQL migration list in `migration_import_runs.source_migrations`. |

Every MySQL index has a PostgreSQL equivalent. A test checks this.

Deliberately **not** added yet (later phases): the "no repeat winner" partial unique
index (randomizer rules), policies, RPC functions and Auth links. The PHP rules stay
the source of truth until those phases.

## 2. Time zone (DATETIME → timestamptz)

The PHP app runs in `APP_TIMEZONE=Asia/Manila`. `Database.php` sets the MySQL session
`time_zone` to `+08:00`. Every stored DATETIME is therefore **Manila wall-clock time
with no zone attached**.

The import reads each value as text, never through JavaScript `Date`, and stores it as:

```sql
'YYYY-MM-DD HH:MM:SS'::timestamp AT TIME ZONE 'Asia/Manila'   -- -> timestamptz
```

For example, `2026-10-10 08:00:00` (Manila) is stored as the instant
`2026-10-10T00:00:00Z`. Manila is UTC+8 with no daylight saving time since 1978, so
the conversion is unambiguous. To show a value in Manila time, use
`to_char(col AT TIME ZONE 'Asia/Manila', …)` or `public.app_time_zone()`.

Caveat: a row inserted into MySQL outside the PHP app (e.g. phpMyAdmin with a server
running in UTC) would hold UTC wall time. That is not detectable after the fact. The
PHP app never does this.

## 3. QR tokens

- **Existing tokens are copied byte for byte.** There is no trim, case change,
  regeneration or hashing. The column is `text COLLATE "C"`, so `Ab` ≠ `ab`, and `-` and
  `_` are significant.
- The CHECK accepts exactly what the registration scanner accepts (16–64 base64url
  characters). It never alters a value. It only refuses one that could not be
  scanned, such as surrounding spaces.
- **New tokens:** `public.generate_qr_token()` returns 24 random bytes from
  `gen_random_bytes` (pgcrypto) encoded as unpadded base64url. That is 32 characters,
  the same format as the PHP `QrCodeService`. Phase 1 does not call it; it is not
  executable by `anon`/`authenticated`.
- A printed QR contains only the token. It keeps working after the move **only if
  the same token is still attached to the same attendee (event_id + attendee_code)**.
  The verifier checks exactly that.

## 4. Security baseline (Phase 1)

- RLS is **enabled on every table with no policies**, and every table, sequence and
  function privilege is revoked from `anon` and `authenticated`. The Data API
  therefore returns nothing. These tables hold attendee personal data, QR tokens and
  password hashes. Later phases add specific policies and RPCs.
- **The service-role / `sb_secret_` key is never used** in React, Vite, Vercel
  environment variables, client code or Git. It may only live in Supabase Edge
  Function secrets (later phases). The tools here connect with a **database
  connection string**, not an API key.
- `frontend/vite.config.ts` refuses to build when a `VITE_*` variable holds a
  service-role or secret key. `supabaseClient.ts` refuses such a key at runtime.
- QR manifests contain names and tokens. Keep them private. They are saved with mode
  0600 into git-ignored `database/qr-migration/`. There is no web endpoint.

### Read-only accounts for verification (recommended)

MySQL source, for the import and the verifier:

```sql
CREATE USER 'holcim_readonly'@'localhost' IDENTIFIED BY '<strong password>';
GRANT SELECT ON holcim_event.* TO 'holcim_readonly'@'localhost';
```

Supabase target, for the verifier. Run this in the SQL editor after the import. It
grants only the columns the verifier reads, and only for this login role:

```sql
create role holcim_verifier login password '<strong password>' nobypassrls;
alter role holcim_verifier set default_transaction_read_only = on;
grant usage on schema public to holcim_verifier;
grant select (id) on public.events to holcim_verifier;
grant select (id, event_id, attendee_code, full_name, company, department, status) on public.attendees to holcim_verifier;
grant select (id, attendee_id, token) on public.attendee_qr_codes to holcim_verifier;
grant select (attendee_id, qr_code_id) on public.registration_scans to holcim_verifier;
create policy migration_verifier_read on public.events             for select to holcim_verifier using (true);
create policy migration_verifier_read on public.attendees          for select to holcim_verifier using (true);
create policy migration_verifier_read on public.attendee_qr_codes  for select to holcim_verifier using (true);
create policy migration_verifier_read on public.registration_scans for select to holcim_verifier using (true);
-- when verification is finished:
-- drop policy migration_verifier_read on public.events; (… each table) ; drop role holcim_verifier;
```

The verifier itself also always reads inside a `READ ONLY` transaction and rolls it
back.

## 5. Running the migration (the real 264-attendee database)

Do this from the computer that has the MySQL database (XAMPP).

1. **Back up MySQL** (keep the file private):
   `mysqldump --single-transaction holcim_event > holcim_event-before-supabase.sql`
2. **Save the QR manifest from MySQL** (current system, read-only):
   `php backend/cli/verify-qr-migration.php --save`.
   The result must be PASS with Attendees 264, QR records 264, and missing, orphan
   and empty all 0. Write down both SHA-256 values.
3. **Create the Supabase project.** Choose a region near the Philippines (e.g.
   Singapore). Apply the migrations by **one** of these methods:
   - Supabase CLI: `supabase link --project-ref <ref>` then `supabase db push`.
   - SQL editor: run the three files in `supabase/migrations/` in filename order.
   - psql: `psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 -f <file>` for each file, in order.
4. **Connection string and TLS.** Go to Project Settings → Database. Use the
   **Session pooler** (port 5432, IPv4) or a direct connection. Do not use the
   transaction pooler on 6543: the import needs one long transaction. Download the
   project **CA certificate** and point to it with
   `export PGSSLROOTCERT=/path/prod-ca-2021.crt`. TLS is always verified.
5. **Dry run.** It copies, verifies, then rolls back:
   ```bash
   cd tools && npm ci
   export MYSQL_URL='mysql://holcim_readonly:<pw>@127.0.0.1:3306/holcim_event'
   export SUPABASE_DB_URL='postgresql://postgres.<ref>:<pw>@aws-0-<region>.pooler.supabase.com:5432/postgres'
   node import-mysql-to-postgres.ts --dry-run --expect-attendees=264 --expect-qr=264
   ```
6. **Import.** Run the same command without `--dry-run`. This step:
   - refuses if the target is not empty, or if the source counts differ;
   - copies all 14 tables with their ids;
   - compares counts and the canonical SHA-256 of every table;
   - compares the QR dataset and identity fingerprints;
   - moves the identity sequences past the imported ids;
   - records the run in `migration_import_runs`.

   Any difference rolls everything back. It never writes to MySQL.
7. **Verify the QR codes against the saved manifest.** This is the Phase 1 gate:
   ```bash
   node verify-qr-migration.ts --db="$SUPABASE_DB_URL" --compare=../database/qr-migration/qr-manifest-<stamp>.json
   ```
   It must print `QR identity mappings preserved: 264/264` and `RESULT: PASS`. The
   identity SHA-256 must equal the one from step 2.

If anything fails, nothing is lost. MySQL was never modified and the PHP system keeps
running. Empty the Supabase schema (drop and re-apply the migrations on the
not-yet-live project) and repeat from step 5.

Environment variables used by the tools: `MYSQL_URL`, `SUPABASE_DB_URL` (or
`DATABASE_URL`), and `PGSSLROOTCERT`. Pass them on the command line or in your shell.
Never commit them.

Frontend (configured, not used yet): `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`.
See `frontend/.env.example`.

## 6. Compatibility notes for later phases

- **Text comparison.** MySQL `utf8mb4_unicode_ci` ignores case, accents and trailing
  spaces. PostgreSQL compares exactly. The `lower()` unique indexes restore case
  insensitivity, but `José`/`Jose` and `abc`/`abc ` are distinct in PostgreSQL. That
  is stricter for lookups and more permissive for uniqueness. Search features must
  use `ILIKE`/`lower()` (or `unaccent`) on purpose.
- **Sorting.** Byte order versus collation order can differ for accented names.
- **JSON** key order and formatting are not kept (jsonb); the values are.
- **Identity sequences** are not transactional (`nextval` gaps are normal), the same
  as MySQL AUTO_INCREMENT.
- **Booleans and enums** remain text values, exactly as the PHP code expects.
- **Row locks.** The PHP `SELECT … FOR UPDATE` patterns (draw day lock, attendee code
  generation) must become `FOR UPDATE` inside RPC functions in later phases.

## 7. Tests

```bash
cd tools
export TEST_MYSQL_ADMIN_URL='mysql://<admin>:<pw>@127.0.0.1:3306'          # may create holcim_migtest_* DBs
export TEST_PG_ADMIN_URL='postgresql://postgres@localhost:5432/postgres'     # local PostgreSQL, NOT Supabase prod
npm run typecheck && npm test
```

The tests only create and drop databases named `holcim_migtest_*`. Without the two
variables, only the pure unit tests run.

Coverage:
- **Schema:** tables, columns, every FK and its rules, every index and unique key,
  enum CHECKs, identity columns, timestamptz, the token collation, triggers, RLS,
  revoked privileges, and the token generator.
- **Constraints:** case-sensitive unique tokens, one QR per attendee, the token
  CHECK, the single active event and day, case-insensitive codes and emails,
  composite FKs, protected history, `updated_at` and the time zone.
- **End to end:** 264 seeded attendees with QR codes and rows in every table, then
  the manifest, the PHP↔TypeScript fingerprint parity, the dry run, the import,
  per-table SHA-256, byte-exact tokens, sequences, time instants and JSON, the
  re-import refusal, and the unchanged source.
- **Mutation scenarios:** a case flip, `-`→`_`, swapped tokens, a missing QR, a changed
  code or a moved event all **FAIL**. Renumbered ids and a company change **PASS**
  and are reported.

The PHP/MySQL tests are unchanged: `backend/tests/*.php`.
